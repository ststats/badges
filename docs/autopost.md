# 멤버 공지 → 와이고수 자동 등록

대상: 상태 화면(`/status`)의 **공지 자동 등록**에서 켠 멤버. 멤버마다 그 멤버의 SOOP 본인 글을 지정한 와고 게시판
(예: `https://ygosu.com/board/pan_이름`)에 올립니다. 여러 명을 켜면 여러 명, 아무도 켜지 않으면 아무 것도 올리지 않습니다.
멤버 목록은 스타유니브의 지금 멤버(퇴단일 없음)이고, 게시판은 주소나 이름(`pan_…`)으로 넣습니다.

SOOP 쿠키가 있으면 즐겨찾기 전용 글까지, 없거나 만료되면 공개 글만 확인합니다(공개 글로 계속 올립니다).
Supabase의 공개 `member_posts` 수집에는 즐겨찾기 본문을 넣지 않습니다.

## 켜고 끄기

- **켜기**: 멤버를 체크하고 게시판을 넣은 뒤 **설정 저장**(편집 비밀번호). 켠 뒤 첫 감지는 그때 글을 기준으로만 저장하고,
  그 다음 새 글부터 올립니다. 켜기 전에 올라온 글은 올리지 않습니다.
- **끄기**: 체크를 풀고 저장. 그 멤버의 감지 상태는 지워지고, 다시 켜면 그때부터 새로 시작합니다.
- **게시판 바꾸기**: 켠 채로 게시판만 바꾸면 다음 새 글부터 바뀐 게시판에 올립니다.
- 게시판에 `공지` 분류가 있으면 그 분류로, 없으면 분류 없이 올립니다.

## 실행 구조와 사용량

기존 Supabase `live-status` cron(2분 주기)에 Vercel `/api/autopost-detect` 호출을 덧붙입니다.
Vercel이 켠 멤버를 차례로 보고, 새 글이 있는 첫 멤버만 GitHub 워크플로를 실행합니다(같은 워크플로의 대기 실행은 하나뿐이라
한 번에 여러 개를 보내면 앞의 것이 취소됩니다). 나머지 멤버는 다음 감지에서 봅니다. 한 멤버의 SOOP 오류는 다른 멤버를 막지 않습니다.
GitHub 자체의 예약 실행은 없습니다. 이미지 생성·와고 로그인·등록은 GitHub에서 처리합니다.
GitHub 작업은 OIDC 신원으로 `/api/autopost-source`에 멤버 SOOP ID를 보내고, Vercel은 켜 둔 멤버일 때만 글과 설정(이름·게시판·켠 시각)을
돌려줍니다. 쿠키와 복호화 키는 Vercel 안에 남습니다. 서버는 GitHub 서명, 저장소/소유자 ID, main, 워크플로 경로를 모두 검증합니다.
등록 작업은 영구 이력을 다시 읽고 `/api/autopost-result`로 완료·재시도·중단을 통보합니다.
GitHub 실행 요청 접수만으로 공지를 처리 완료로 기록하지 않습니다.

2분 간격은 실시간 푸시가 아닙니다. GitHub 실행 대기 시간도 추가됩니다.
Vercel 호출은 30일 기준 21,600회이며, 켠 멤버 수만큼 SOOP 조회가 늘어납니다. CPU·메모리·전송량도 기존 뱃지와 함께 한도를 사용합니다.
첫 페이지의 최신 글만 대상으로 하므로 오래 중단되었다고 과거 페이지를 모두 조회하지 않습니다.

## 디자인

와고 제목은 원문 공지 작성일과 멤버 이름을 쓴 `261012 이름 공지` 형식입니다. 원문 제목은 전체 공지 이미지 안에 표시합니다.

기존 뱃지와 같은 프로필/파스텔 머리/흰 카드에 **전체 제목·본문·사진**을 담습니다.
원문 문단·사진 순서를 유지하고 별도 첨부 사진도 모두 넣습니다.
본문 줄 수·사진 수를 제한하거나 사진을 썸네일로 자르지 않습니다.
긴 공지는 약 1800px마다 이어지는 PNG로 나눠 한 글에 순서대로 업로드하고 원문 링크를 붙입니다.
GIF는 캡처 시점 정지 화면입니다. 영상·본문 누락·이미지 다운로드 실패·지원하지 않는 이미지 호스트는 생략하지 않고 실행을 중단합니다.
원문 이미지는 SOOP/아프리카 도메인만 허용합니다.

## 설정과 활성화 순서

GitHub Actions Secrets에는 `YGOSU_ID`, `YGOSU_PASSWORD`만 등록합니다. 이 와고 계정이 켠 멤버들의 게시판에 글을 쓸 수 있어야 합니다.
`SOOP_COOKIE`와 `COOKIE_KEY`는 GitHub에 추가하지 않습니다.
와고는 매 실행마다 아이디/비밀번호로 로그인합니다. 추가 인증·캡차·권한 문제가 있으면 중단합니다.
SOOP 쿠키가 만료되면 기존 상태 화면에서 갱신합니다.

1. Supabase SQL Editor에서 `supabase/autopost.sql`을 실행합니다. 한 멤버 전용이던 이전 감지 표·함수를 지우고 멤버별 표·함수를 만듭니다.
2. 코드를 main에 병합하고 Vercel 배포 성공을 확인합니다.
3. 이력 브랜치 `autopost-state`가 있어야 합니다(멤버마다 `targets/<SOOP ID>.json`을 첫 등록 때 만듭니다).
   완전히 새로운 설치라면 운영자가 orphan 브랜치 `autopost-state`를 먼저 만듭니다. 브랜치가 없으면 자동으로 만들지 않고 중단합니다.
   GitHub Variable `AUTOPOST_ENABLED=true`를 설정합니다.
4. GitHub의 fine-grained PAT를 이 저장소만 선택하고 **Actions: Read and write** 권한으로 생성합니다.
   Vercel Production의 민감 환경 변수 `GITHUB_DISPATCH_TOKEN`에 저장합니다. 코드·Variables·채팅에 넣지 않습니다.
5. Vercel Production에 `AUTOPOST_DETECT_ENABLED=true`를 설정하고 다시 배포합니다.
   기존 `BADGE_WRITE_SECRET`과 Supabase Vault의 `badge_write_secret`을 그대로 사용합니다.
6. `supabase/autopost-tick.sql`을 실행합니다(이미 실행했다면 다시 할 필요 없음). 기존 작업과 2분 주기를 검증하고, 호출을 중복 없이 추가합니다.
7. 상태 화면에서 멤버를 켭니다.

Supabase `ststat.sql`로 live-status cron을 다시 만들었다면 마지막 tick SQL도 다시 실행해야 합니다.
전체를 멈출 때는 GitHub Variable `AUTOPOST_ENABLED=false`를 설정합니다. 한 멤버만 멈출 때는 상태 화면에서 끕니다.
감지 호출도 멈추려면 기존 cron 명령에서 `badges-autopost-tick-v1` 블록만 제거합니다.

## 폭주·중복 방지

수동 실행에는 항상 멤버 SOOP ID(`target`)를 넣습니다. 켜 둔 멤버만 실행됩니다.
이미 기준 저장을 마친 상태에서 등록 테스트하려면 수동 실행의 `publish_latest`를 켭니다.
최신 글 하나만 대상으로 하며, 이미 등록한 글은 재등록하지 않습니다. pending과 5분 간격 제한도 유지합니다.

멤버마다 최신 새 글 **딱 하나만** 등록합니다. 밀린 나머지 글은 건너뛰며 그 멤버의 마지막 성공 등록 후 5분 이내 추가 등록하지 않습니다.
Supabase 감지 상태에는 멤버별 글 번호·시각·잠금만 저장하고 켠 뒤 첫 감지는 기준 저장만 합니다.
행 잠금과 실행별 UUID로 동시 감지를 막습니다. GitHub 실행 대기를 포함해 20분 동안 완료 통보를 기다립니다.
준비 실패·5분 게시 간격으로 인한 보류는 5분 후 재시도하며, 강제 취소/시간 초과 등 통보가 없으면 임대 만료 후 재시도합니다.
같은 최신 공지는 최초 실행 포함 최대 3회 시도하고 `retry_limit`에서 멈춥니다. 새 공지의 시도 횟수는 별도로 시작합니다.
미확정 pending이나 읽을 수 없는 이력은 그 멤버를 `blocked`로 멈춥니다(상태 화면에 표시). 다른 멤버는 계속합니다.
GitHub 동일 워크플로는 한 번에 하나만 실행합니다.
전용 orphan `autopost-state` 브랜치에는 멤버별로 시작 시각·SOOP 번호·와고 번호만 기록하며 본문·인증 정보를 저장하지 않습니다.
이 브랜치를 Vercel Preview 배포 대상으로 추가하지 마세요.

등록 요청 **전에** 영구 `pending`을 저장하고 SHA 충돌 검사를 적용합니다.
등록 멱등키는 와고 게시판과 SOOP 원문 번호로 고정하며, 재등록용 키 오버라이드는 지원하지 않습니다.
응답이 불확실하거나 등록 후 상태 저장이 실패하면 그 멤버의 다음 실행도 중단해 중복 게시를 막습니다.
이미지 준비 오류는 재시도할 수 있습니다. 원문 수정·삭제는 이미 등록한 고정 이미지에 자동 반영하지 않습니다.
GitHub 로그/artifact에 본문·쿠키·스크린샷을 남기지 않습니다.

어떤 멤버에 `pending`이 남으면:

1. 상태 화면에서 그 멤버를 끄고(또는 전체를 `AUTOPOST_ENABLED=false`로 중지) 와고 등록 결과를 직접 확인합니다.
2. 등록되었다면 `targets/<SOOP ID>.json`의 `done`에 `"SOOP번호": 와고글번호`를 추가하고 `pending`을 삭제합니다.
   확실히 등록되지 않았고 pending 생성 후 1시간 이내라면, 결과 확인을 마친 뒤 그 멤버를 켜 둔 상태에서
   수동 실행의 `target`에 SOOP ID를, `recover_pending`에 해당 SOOP 번호를 정확히 입력해 같은 멱등키로 한 건만 복구합니다.
   시간이 지났거나 결과가 불확실하면 pending을 유지하고 수동 점검합니다. 상태 파일 전체를 지우지 마세요.
3. 이력 복원/복구가 완료되고 pending이 없음을 확인한 뒤 상태 화면에서 그 멤버를 다시 켭니다(껐다 켜면 감지 상태가 새로 시작합니다).

`retry_limit`도 원인을 해결한 후 껐다 켜서 다시 시작합니다.
수동 실행의 `delivery_lease`와 `delivery_title`은 비워 둡니다. 감지기가 자동 실행을 요청할 때만 채웁니다.
`diagnose_only`는 인증/글쓰기 폼 확인용이며 게시와 이력 변경을 하지 않습니다(`target` 멤버의 게시판으로 확인).

## 검증

`npm test`: 수집(쿠키 실패 시 공개 글)·최신 하나·멤버별 감지·중복 방지·등록 전후 상태 저장·내용 보존·OIDC 신원·감지/완료/실패 경로 검증.
`tests/autopost-delivery.sql`: 실제 DB 함수의 켜기/끄기·재시도 상한·완료 확인·오래된 통보 거절을 트랜잭션 안에서 검증하고 롤백합니다.
`npx playwright install chromium && node scripts/preview-autopost.mjs`: 합성 긴 공지의 이미지 전체 생성·분할 검증.
실계정 로그인·업로드·등록과 Supabase/Vercel 연결은 별도 운영 검증이 필요합니다.

## DB 접근 권한

설정·감지 표는 RLS와 직접 접근 권한 회수로 외부 조회/수정을 막습니다.
RPC는 기존 공개 API 키 연결을 유지하되 Vault의 `badge_write_secret`을 먼저 검사하고 빈 search_path와 스키마 명시를 사용합니다.
따라서 Supabase advisor의 [anon SECURITY DEFINER 경고](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable)는 이 RPC에 대해 의도된 구조입니다. 잘못된 비밀값의 거절도 테스트합니다.
